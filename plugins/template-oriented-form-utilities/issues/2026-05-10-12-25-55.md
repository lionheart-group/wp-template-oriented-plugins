# Feature: Record Submitted Form Data to Database After Email Dispatch

**Date:** 2026-05-10  
**Updated:** 2026-05-10 (encryption + field-selection; review feedback: title, flow diagram, submitted_at timezone; migration infrastructure extended to support ALTER TABLE via useRawQuery())  
**Status:** Planned

---

## Overview

`FormConfig` already exposes a `saveToDatabase` flag (default `false`) with a `@todo` marker, and the `wp_tofu_records` table is created on plugin activation by an existing migration. However, neither the `Record` model nor the form processing pipeline actually saves any field data.

This issue tracks all the work required to make `saveToDatabase: true` fully functional: store validated, submitted form values in `wp_tofu_records` immediately after emails are sent successfully. The stored payload is **encrypted at rest** using the existing `Encryptor` helper (AES-256-CBC, keyed from WordPress `AUTH_KEY` + `SECURE_AUTH_KEY`), and the developer can opt into recording only a specific subset of fields via a new `records` property on `FormConfig`.

### Flow where the record should be written

```
processConfirm()
  └─ [all emails sent successfully]
  └─ ← insert record here (when saveToDatabase === true)
  └─ [delete temp uploaded files]
  └─ storeSession(flushValue)
  └─ return success
```

## Goals

1. Extend the migration runner to support raw SQL execution (required for `ALTER TABLE`).
2. Extend `wp_tofu_records` with the columns needed to store form data via `ALTER TABLE`.
3. Expand the `Record` model to declare those columns and provide a dedicated save method.
4. Encrypt the stored payload using `Encryptor::encrypt()` so data is secured at rest.
5. Add a `records` property to `FormConfig` to let developers specify exactly which fields to persist.
6. Integrate the record-save call into `processConfirm()` after emails succeed.
7. Keep the feature strictly opt-in via `saveToDatabase: true` in `FormConfig`.

## Detailed Tasks

### 0. Extend the migration infrastructure to support raw SQL

The current `Migration` base class (`src/Base/Migration.php`) only defines `sql(): string`, and `Migrate::migrate()` (`src/Init/Migrate.php`) unconditionally passes that SQL to `dbDelta()`. `dbDelta()` is designed for `CREATE TABLE` statements and does not reliably execute `ALTER TABLE` or other DDL statements.

To support `ALTER TABLE` migrations:

**`src/Base/Migration.php`** — add a new method with a default implementation:

```
useRawQuery(): bool   // returns false by default
```

When `useRawQuery()` returns `true`, the migration runner must execute the SQL via `$wpdb->query()` instead of `dbDelta()`. Existing migrations are unaffected (they do not override the method, so they continue to use `dbDelta()`).

**`src/Init/Migrate.php` → `migrate()`** — branch on `useRawQuery()`:

```
// (pseudo-code, not literal)
$sql = $migrateClass->sql();
if ($migrateClass->useRawQuery()) {
    $wpdb->query($sql);
} else {
    dbDelta($sql);
}
```

This change is backward-compatible: all existing migrations (`2024-08-29_…`, `2025-12-23_…`) continue to work without modification.

### 1. Add a DB migration for new columns

Create a new migration file (e.g. `migrations/2026-05-10_00-00-00_records-add-data-column.php`) as an anonymous class extending `Migration`.

- Override `useRawQuery(): bool` to return `true` — this instructs the updated runner to execute the SQL via `$wpdb->query()`.
- The `sql()` method should execute two `ALTER TABLE` statements (one per column) to add:

| Column | Type | Notes |
|---|---|---|
| `data` | `LONGTEXT` | AES-256-CBC encrypted, base64-encoded payload (see §3) |
| `submitted_at` | `DATETIME` | UTC timestamp set from PHP via `current_time('mysql', true)` — **no DB default** |

> **MySQL compatibility — column-existence guard**  
> `ALTER TABLE … ADD COLUMN IF NOT EXISTS` is only available in MySQL 8.0.3+ and MariaDB 10.0+. WordPress supports older MySQL versions, so the migration must guard against running `ALTER TABLE` when the column already exists.  
> The recommended approach is to check `SHOW COLUMNS FROM {$table} LIKE 'column_name'` via `$wpdb->get_results()` before issuing each `ALTER TABLE`. If the column is already present, skip that statement. This makes the migration idempotent across all supported MySQL versions.
>
> **Why `ALTER TABLE` instead of `dbDelta()` + `CREATE TABLE`?**  
> `dbDelta()` can add missing columns when given a full `CREATE TABLE` definition. However, `ALTER TABLE` is the explicit and unambiguous way to evolve an existing table schema, and is the approach required by this project. The `useRawQuery()` hook introduced in Task 0 makes this safe without affecting any existing migration.
>
> **Why no `DEFAULT CURRENT_TIMESTAMP` on `submitted_at`?**  
> `CURRENT_TIMESTAMP` uses the DB server/session timezone, which may not be UTC. `submitted_at` is always set explicitly in PHP via `current_time('mysql', true)` (WordPress's UTC-aware helper), so no DB default is needed.

Register the new migration key in the array inside `Migrate::migrate()`.

### 2. Add `records` field to `FormConfig`

Add a new constructor parameter to `src/Structure/FormConfig.php`:

```
records: string[]   // default: [] (empty = record all fields in `allows`)
```

Behaviour:
- `[]` (default) — when `saveToDatabase: true`, all fields listed in `validation->allows` are included in the payload.
- Non-empty array — only the field names in this list are included; fields absent from `validation->allows` are silently skipped.
- The `records` list is independent of `allows`; it is a further filter, not a replacement.

This lets developers exclude sensitive fields (e.g. passwords, payment tokens) from the persisted record without changing validation rules.

### 3. Extend `Record` model columns and add encrypted save method

Update `src/Models/Record.php`:

- Add `data` as `COLUMN_STRING`.
- Add `submitted_at` as `COLUMN_DATETIME`.
- Add a static helper method `Record::saveRecord(string $formKey, array $values, array $recordFields = []): int|false` that:
  1. If `$recordFields` is non-empty, filters `$values` to only the keys listed there.
  2. Passes the (possibly filtered) values array to `Encryptor::encrypt()` — which internally JSON-encodes and AES-256-CBC encrypts the data, returning a base64-encoded ciphertext string.
  3. Calls `static::insert(['form_id' => $formKey, 'data' => $encrypted, 'submitted_at' => current_time('mysql', true)])`.
  4. Returns the inserted row ID on success, or `false` on failure.

> **Why `Encryptor::encrypt()`?**  
> `Encryptor` already exists, is used for session flush values, and is keyed from WordPress's `AUTH_KEY` + `SECURE_AUTH_KEY` constants (SHA-256 derived, 32 bytes). Using it here keeps encryption consistent across the plugin and requires no new dependencies.

### 4. Integrate into `Form::processConfirm()`

In `src/Models/Form.php`, after the loop that sends emails and before the temp-file deletion block:

```
// (pseudo-code, not literal)
if ($this->config->saveToDatabase) {
    $recordId = Record::saveRecord(
        $this->config->key,
        $values,
        $this->config->records,   // field filter — empty means all allowed fields
    );
    if ($recordId === false) {
        Logger::error('Failed to save record', ['form_key' => $this->config->key]);
        // Non-fatal: log and continue — do not abort the successful submission
    }
}
```

**Important design decision:** A record-save failure must **not** abort the submission (emails already sent). Log the error and continue to the success path.

### 6. Add unit / integration tests

- Test `Record::saveRecord()` — assert that the value stored in `data` can be round-tripped through `Encryptor::decrypt()` and yields the expected field values.
- Test field filtering: when `$recordFields` is set, assert that only those keys appear after decryption.
- Test `processConfirm()` with `saveToDatabase: true` — verify `Record::saveRecord()` is called after email success.
- Test `processConfirm()` with `saveToDatabase: false` — verify no DB write occurs.
- Test `processConfirm()` when `saveRecord()` returns `false` — verify the submission still succeeds (non-fatal).
- Test `FormConfig` with `records` specifying a subset — verify only those fields are saved.

## Acceptance Criteria

- [ ] Migration runs cleanly on a fresh install and on an existing install (idempotent via column-existence guards or migration version check).
- [ ] `saveToDatabase: false` (default) produces zero DB writes — existing behaviour unchanged.
- [ ] `saveToDatabase: true` with `records: []` inserts one row per successful submission; the `data` column contains a ciphertext that decrypts to all fields listed in `validation->allows`.
- [ ] `saveToDatabase: true` with `records: ['name', 'email']` — the decrypted payload contains only those two fields, even if more fields were submitted and validated.
- [ ] `Encryptor::decrypt($row->data)` returns the original field-value array (round-trip verified in tests).
- [ ] A record-save failure does not prevent the result page from loading or the flush value from being set.
- [ ] PHPStan passes at the existing level with no new errors.
- [ ] All existing tests continue to pass; new tests cover the scenarios listed above.
