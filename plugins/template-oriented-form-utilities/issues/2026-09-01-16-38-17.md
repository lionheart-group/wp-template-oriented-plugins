# Feature: HTML Mail Support via a MailRecipientsConfig Property

**Date:** 2026-09-01
**Status:** Open

---

## Overview

TOFU can only send `text/plain` email. `Models\Mail::send()` never sets a `Content-Type` header, so
`wp_mail()` falls back to its plain-text default, and there is no configuration path to change that.

This was raised while designing the plugin's first set of hooks (see the hooks work that added
`tofu_pre_send_mail` and friends). It was deliberately **excluded** from that work: whether a form's
mail is HTML is a property of *what that form is*, decided by whoever wrote the `MailRecipientsConfig`
— not something an unrelated plugin should reach in and change. By the rule of thumb recorded in
`CLAUDE.md` ("config describes what a form *is*; a hook describes what the site *does*"), it belongs
in configuration.

`tofu_pre_send_mail` does technically allow `$mail->addHeader('Content-Type: text/html; charset=UTF-8')`
as an interim workaround, but that is not the intended path and is deliberately not documented as
such in `docs/hooks/index.md`.

## Background

| Component | Location | Current state |
|---|---|---|
| Mail dispatch | `src/Models/Mail.php:224-248` (`send()`) | Flattens Cc/Bcc/From into `$headers`, then calls `wp_mail()`. No `Content-Type` is ever added. |
| Header API | `src/Models/Mail.php:200-204` (`addHeader()`) | Public, returns `$this`, but nothing inside the plugin calls it — dead from the caller's side until the hooks work. |
| Mail assembly | `src/Models/Form.php` (`processConfirm()`, recipient loop) | Builds one `Mail` per recipient: `setFrom` → `addTo` → subject → body → cc → bcc → attachments → `tofu_pre_send_mail` → `send()`. |
| Recipient config | `src/Structure/MailRecipientsConfig.php:14-91` | `recipientEmail`, `recipientCcEmail`, `recipientBccEmail`, `subject`, `subjectPath`, `mailBody`, `mailBodyPath`. Ctor throws when neither subject source, or neither body source, is set. |
| Placeholder expansion | `src/Helpers/Template.php:34-51` (`replaceBracesValues()`) | `{field}` → value via `preg_replace`. Arrays/objects are JSON-encoded. **Performs no escaping whatsoever.** |
| Template bodies | `src/Models/Mail.php:156-192` | `setSubjectFromTemplate()` / `setBodyFromTemplate()` render via `Template::getTemplateContent()`, which is `ob_start()` + `get_template_part()`. These do *not* go through `replaceBracesValues()`. |

### The escaping problem

This is the substantive design question, not the plumbing.

`replaceBracesValues()` substitutes submitted values into `subject` / `mailBody` **raw**. For
`text/plain` that is harmless. The moment the body is sent as `text/html`, any submitted value
containing markup is interpolated into an HTML document — a visitor typing `<script>` or, more
realistically, `<` and `>` in a free-text field produces broken or hostile markup in the recipient's
mail client.

Note the asymmetry: static `mailBody` strings go through `replaceBracesValues()`, but
`mailBodyPath` template files do not receive values through it at all (`getTemplateContent()` is
currently called with no `$args`), so template authors are already responsible for their own output.

Three candidate policies, to be decided as part of this issue:

1. **Escape on the HTML path only** — give `replaceBracesValues()` an opt-in `$escape` argument and
   apply `esc_html()` to substituted values when the recipient is configured as HTML. The existing
   `text/plain` behaviour stays byte-identical. Open sub-question: whether newlines should become
   `<br>` (probably not — leave that to the template).
2. **Escape nothing; document it** — keep current behaviour and state in the docs that HTML bodies
   must be built via `mailBodyPath` with escaping done in the template.
3. **Refuse the risky combination** — allow `isHtml` only alongside `mailBodyPath`, and throw from
   the `MailRecipientsConfig` constructor when it is combined with a static `mailBody`. Closes the
   raw-interpolation path structurally rather than by convention.

Option 1 is the most useful and the least surprising; option 3 is the most conservative. Worth
deciding before writing code, since it determines the shape of the config property.

---

## Goals

1. Let a form declare that a recipient's mail is HTML, in configuration rather than through a hook.
2. Decide and implement an escaping policy for values interpolated into an HTML body.
3. Leave `text/plain` behaviour — the default for every existing form — completely unchanged.
4. Keep `Mail` unaware of form configuration: it should receive a finished header, as it does today.

---

## Detailed Tasks

### 1. Decide the escaping policy

Settle on option 1, 2 or 3 above before implementing. The rest of this issue assumes a property
exists; its exact validation rules depend on this choice.

### 2. Add the property to `MailRecipientsConfig`

`src/Structure/MailRecipientsConfig.php` — follow the existing promoted-readonly + named-argument
style:

```php
public readonly bool $isHtml = false,
```

Consider `?string $contentType = null` instead if there is any appetite for other content types;
`bool` is the simpler surface and can widen later without breaking callers, whereas the reverse is
not true. If option 3 is chosen, add the constructor guard alongside the existing subject/body
guards at `:79-90`.

### 3. Set the header during mail assembly

`src/Models/Form.php`, in the recipient loop, after the attachment loop and **before** the
`tofu_pre_send_mail` action (so a site can still override it):

```php
if ($recipient->isHtml) {
    $mail->addHeader('Content-Type: text/html; charset=UTF-8');
}
```

`Mail::addHeader()` already exists and needs no change.

### 4. Apply the chosen escaping

If option 1: add an `$escape` parameter to `Helpers\Template::replaceBracesValues()`, defaulting to
`false` so every existing call site is unaffected, and pass `true` from the subject/body/cc/bcc
interpolation calls when `$recipient->isHtml`. Note that recipient/cc/bcc addresses should *not* be
HTML-escaped — only the subject and body are rendered as markup, and the subject arguably not even
then.

### 5. Tests

- A recipient with `isHtml: true` sends a `Content-Type: text/html` header; the default sends none.
- Existing plain-text forms produce byte-identical headers and body (regression guard).
- Whichever escaping policy is chosen, a submitted value containing `<`/`>`/`&` behaves as decided.
- `tofu_pre_send_mail` can still override the header afterwards.

`tests/bootstrap.php` already records every `wp_mail()` call in `$GLOBALS['__tofu_wp_mail_calls']`
(added during the hooks work), so header assertions need no new scaffolding.

### 6. Documentation

- `docs/settings/mailrecipientsconfig.md` — document the property and the escaping policy, with a
  worked HTML example.
- `docs/hooks/index.md` — the `tofu_pre_send_mail` section currently avoids HTML examples on purpose;
  once this ships, point readers at the config property from there.
- `readme.txt` — changelog entry at release time.
