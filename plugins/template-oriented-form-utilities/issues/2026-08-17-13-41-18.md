# Feature: Allow Per-Page Dynamic Template URLs for Embedded Forms

**Date:** 2026-08-17
**Updated:** 2026-08-17 (implemented; also fixed a pre-existing `tests/bootstrap.php` bug where the missing `WPINC` constant caused `composer test` to silently truncate the suite partway through — see Acceptance Criteria)
**Status:** Implemented

---

## Overview

`TemplateConfig::$inputPath`, `$confirmPath`, and `$resultPath` are currently fixed strings decided once at `FormConfig` registration time (typically on `init` in `functions.php`). This works for a form that lives on exactly one URL, but breaks down when the same form key is embedded on many pages whose URLs are only known at render time — most notably a form embedded in post/article templates (e.g. `/news/{slug}/contact/`), where every post has a different `inputPath`, and the matching `confirmPath` / `resultPath` should follow the same post.

This issue tracks adding a way to override a form's template paths per-request, from the theme, at render time — so a single registered form can be embedded on an arbitrary number of pages, each with its own input/confirm/result destination, without registering a separate `FormConfig` per page.

---

## Background

### Existing infrastructure

| Component | Location | Current state |
|---|---|---|
| `TemplateConfig` | `src/Structure/TemplateConfig.php` | Immutable `readonly` value object; `inputPath`, `resultPath` required strings, `confirmPath` optional string, set once at registration |
| `FormConfig::$template` | `src/Structure/FormConfig.php` | `?TemplateConfig`, passed once to the constructor; ctor throws if `confirmStep` is true but `template?->confirmPath` is empty (lines ~126-131) |
| Redirect logic | `src/Models/Form.php → redirect()` | Reads `$this->config->template->{inputPath,confirmPath,resultPath}` directly and passes the raw string to `wp_safe_redirect()` — no `home_url()` prefixing, no URL construction |
| Session storage | `src/Helpers/Session.php`, `src/Models/Session.php` | `Session::save()`/`Session::get()`/`Session::clear()` — encrypted (`Encryptor`), keyed by `(form_id, session_key)` in `wp_tofu_sessions`; cookie `_tofu_session_key` is already set on **every** request that constructs a `Models\Form` (`Helpers\Session::getSessionId()` calls `setcookie()` unconditionally) |
| Session lifecycle in `Models\Form` | `src/Models/Form.php` (constructor, `storeSession()`) | Constructor loads `values`/`errors`/`files`/`flushValue` from `Session::get()`; `storeSession()` **overwrites the entire session row** with exactly those four keys on every call |
| Submit endpoint | `src/Init/Endpoint.php` | Handles `?_tofu_key=<base64 JSON {key, action}>` on `template_redirect`, then calls `$form->action($decoded['action'])` and `exit`s — **no theme template is executed** for this request |
| Form action URL | `src/Models/Form.php → getActionUrl()` | Always builds `home_url('/') . '?_tofu_key=...'` — submissions always POST to the site root, regardless of which page the form was rendered on |

### Why the theme can't just pass the URL through the request

```
[GET /news/hello-world/]                 [POST /?_tofu_key=...]              [GET /news/hello-world/confirm/]
   single.php runs                          Init\Endpoint::init()               confirm.php runs
   Form::formOpen()/formClose()             $form->action('input')              Form::verifySession()
   (theme knows the post's URL here)        Models\Form::redirect('confirm')    (theme needs the post's URL again,
                                             (theme is NOT involved here) ─────▶  but this is a fresh page load)
```

The theme only "knows" the current post between the input-page GET and the confirm/result page GETs — never during the intermediate POST, which is handled entirely inside the plugin (`Init\Endpoint` → `Models\Form::action()` → `redirect()`). Any per-page override supplied while rendering the input page must therefore be **persisted somewhere the POST and the later GETs can all read it from** — the session is the natural fit, since it is already the mechanism that survives exactly this request boundary for `values`/`errors`/`files`/`flushValue`.

> **Why not a query-string parameter or a filter hook instead of the session?**
> A query-string parameter would have to survive an unauthenticated, unsigned round trip through the `_tofu_key` payload — anyone could tamper with it to redirect other users' submissions to an arbitrary URL. A `apply_filters()` hook was also considered, but the plugin currently has **zero** filters or actions anywhere in `src/` (confirmed by repo-wide search), and a filter would still need some way to know "which post was this submission started from," which is the same problem restated. Storing the override in the encrypted, already-cookie-scoped session reuses infrastructure that exists for exactly this purpose and requires no new trust boundary.

---

## Goals

1. Let a theme set the input/confirm/result URLs for the *current visitor's* form session at render time, overriding the static `TemplateConfig` given at registration.
2. Make the override survive the `input` POST → `confirm` GET → `confirm` POST → `result` GET request chain, without theme code running in between.
3. Keep the plugin's config surface unopinionated about URL shape — no slug/placeholder syntax, no `home_url()` assumptions. The theme passes whatever finished string it wants (typically `get_permalink()` plus a suffix).
4. Preserve full backward compatibility: forms that never call the new API must behave exactly as before.
5. Reject or fall back safely if a theme supplies a URL pointing off-site, so `wp_safe_redirect()`'s same-host behavior isn't silently subverted into something worse.
6. Relax the `FormConfig` constructor guard that currently requires `template->confirmPath` to be non-empty whenever `confirmStep` is true, since a dynamic-only setup may legitimately have no static `confirmPath` at registration time.

## Detailed Tasks

### 1. Add an in-session template override to `Models\Form`

**`src/Models/Form.php`** — add a property alongside the existing `$flushValue`:

```php
/**
 * Per-session template override, set via setTemplate().
 * Takes priority over $this->config->template when present.
 *
 * @var ?TemplateConfig
 */
protected ?TemplateConfig $templateOverride = null;
```

In the constructor, alongside the existing `flushValue` restore block (`if (isset($sessionValues['flushValue'])) { ... }`), add:

```php
if (isset($sessionValues['template']) && is_array($sessionValues['template'])) {
    $this->templateOverride = new TemplateConfig(
        inputPath: $sessionValues['template']['inputPath'],
        resultPath: $sessionValues['template']['resultPath'],
        confirmPath: $sessionValues['template']['confirmPath'] ?? null,
    );
}
```

Add a resolver method used everywhere the plugin currently reads `$this->config->template` for URL purposes:

```php
protected function getTemplate(): ?TemplateConfig
{
    return $this->templateOverride ?? $this->config->template;
}
```

### 2. Persist the override through every `storeSession()` call

`storeSession()` (`src/Models/Form.php`, ~line 239) currently writes exactly four keys (`values`, `errors`, `files`, `flushValue`), **replacing the whole session row** every time it's called. If the override isn't included here, it disappears the moment `actionInput()` calls `storeSession()` after the POST.

```php
protected function storeSession(?string $flushValue = null): void
{
    Session::save($this->config->key, [
        'values' => $this->values->toArray(),
        'errors' => $this->errors->toArray(),
        'files' => $this->files->toArray(),
        'flushValue' => $flushValue,
        'template' => $this->templateOverride === null ? null : [
            'inputPath' => $this->templateOverride->inputPath,
            'resultPath' => $this->templateOverride->resultPath,
            'confirmPath' => $this->templateOverride->confirmPath,
        ],
    ]);
}
```

> **Why re-serialize instead of storing the `TemplateConfig` object directly?**
> Session values pass through `Encryptor::encrypt()`/`decrypt()`, which round-trips via JSON (see the existing `Record`/session usage elsewhere in the plugin) — plain arrays are the safest thing to put through that path, consistent with how `values`/`errors`/`files` are already stored as arrays rather than objects.

### 3. Add `Models\Form::setTemplate()`

```php
/**
 * Override this form's template paths for the current visitor's session.
 *
 * Call from a theme template while rendering the input page, before
 * Form::formOpen(). The override is persisted to the session and
 * takes priority over the static TemplateConfig for this visitor
 * until the session is cleared (see verifySubmit()).
 *
 * @param TemplateConfig $template
 * @return void
 */
public function setTemplate(TemplateConfig $template): void
{
    foreach ([$template->inputPath, $template->resultPath, $template->confirmPath] as $path) {
        if ($path !== null && !$this->isSameHostOrRelative($path)) {
            Logger::warning('Rejected cross-host template override', ['form_key' => $this->config->key, 'path' => $path]);
            return; // Ignore the whole override; static config remains in effect.
        }
    }

    $this->templateOverride = $template;
    $this->storeSession($this->flushValue);
}
```

Add a small same-host guard (private helper on `Models\Form`, or a static helper on `Helpers\Directory`/a new `Helpers\Url` if that fits the existing helper layout better):

```php
private function isSameHostOrRelative(string $path): bool
{
    if ($path === '' || $path[0] === '/') {
        return true; // root-relative — always same-host by construction
    }
    $host = wp_parse_url($path, PHP_URL_HOST);
    return $host === null || $host === wp_parse_url(home_url(), PHP_URL_HOST);
}
```

> **Why validate the host here instead of relying on `wp_safe_redirect()`?**
> `wp_safe_redirect()` already refuses cross-host redirects and falls back to `wp_login_url()`/home — so an unchecked override is not an open-redirect vulnerability. But silently sending a legitimate visitor to `/wp-admin/` after they fill out a contact form is a bad failure mode. Validating early lets the plugin log a clear warning and fall back to the static `TemplateConfig` instead.

### 4. Expose the API on the `Helpers\Form` façade

**`src/Helpers/Form.php`**, next to `redirect()`:

```php
/**
 * Override the input/confirm/result URLs for this visitor's session.
 *
 * @param string $key
 * @param TemplateConfig $template
 * @return void
 */
public static function setTemplate(string $key, TemplateConfig $template): void
{
    $form = self::get($key);
    $form->setTemplate($template);
}
```

Typical theme usage (single.php, rendering the input page embedded in a post):

```php
use TofuPlugin\Helpers\Form;
use TofuPlugin\Structure\TemplateConfig;

Form::setTemplate('contact', new TemplateConfig(
    inputPath: get_permalink(),
    confirmPath: get_permalink() . 'confirm/',
    resultPath: get_permalink() . 'thanks/',
));

echo Form::formOpen('contact', 'input');
// ... fields ...
echo Form::formClose('contact', 'input');
```

### 5. Route `redirect()` through the resolved template

**`src/Models/Form.php → redirect()`** (currently ~lines 648-681) — replace every `$this->config->template->...` read with `$this->getTemplate()->...`:

```php
public function redirect(string $action): void
{
    $template = $this->getTemplate();

    if ($template === null) {
        wp_die('Template is not configured for this form.', 'TOFU Form Config Error', ['response' => 500]);
    }

    if (!in_array($action, ['input', 'confirm', 'result'])) {
        wp_die('Invalid action.', 'TOFU Form Action Error', ['response' => 400]);
    }

    $redirectUrl = match ($action) {
        'input' => $template->inputPath,
        'confirm' => $template->confirmPath,
        'result' => $template->resultPath,
        default => null,
    };

    if ($redirectUrl === null) {
        wp_die('Redirect URL is not configured.', 'TOFU Form Action Error', ['response' => 500]);
    }

    wp_safe_redirect($redirectUrl);
    exit;
}
```

(Switching `switch` to `match` here is optional cleanup, not required — keep the existing `switch` if preferred, just change the three right-hand sides to read from `$template` instead of `$this->config->template`.)

### 6. Relax the `FormConfig` constructor guard

**`src/Structure/FormConfig.php`** (~lines 126-131) currently throws when `confirmStep` is true, AJAX is off, and `template?->confirmPath` is empty. A form that is *only* configured dynamically via `setTemplate()` may have no static `confirmPath` at all, so this guard needs to become opt-in-aware rather than hard-fail.

Recommended approach: add a constructor parameter, e.g. `bool $dynamicTemplate = false`, that skips the guard when true:

```php
if (
    $this->confirmStep &&
    !$this->ajaxEnabled &&
    !$this->dynamicTemplate &&
    empty($this->template?->confirmPath)
) {
    throw new \InvalidArgumentException(
        "FormConfig '{$this->key}': confirmStep is true but template->confirmPath is not set. " .
        'For the redirect flow set template->confirmPath (or dynamicTemplate: true if it is supplied ' .
        'per-request via Form::setTemplate()); for AJAX / headless set ajaxEnabled: true.'
    );
}
```

> **Why a new flag instead of just relaxing the check unconditionally?**
> The guard exists to catch a real misconfiguration at registration time (forgetting `confirmPath` entirely). Removing it outright would let that mistake through silently for every form, not just dynamic ones. An explicit `dynamicTemplate: true` documents the intent at the registration site and keeps the safety net for the common case.

### 7. Handle the interaction with `verifySubmit()` clearing the session

`verifySubmit()` (`src/Models/Form.php`, ~lines 623-645) clears the session (`Session::clear()`) once the result page has been verified. Since `$this->templateOverride` is session-backed, the override is gone after that point — which is correct (the visit is over), but means a subsequent `Form::redirect($key, 'input')` call from the *result* page (e.g. on a failed `verifySubmit()`) falls back to the **static** `TemplateConfig::$inputPath`, not the post the visitor originally came from. Document this explicitly in code comments and in the docs update below — it is expected behavior, not a bug, but easy to be surprised by.

## Out of Scope (future issues)

- AJAX / headless mode: `RestEndpoint` never reads `TemplateConfig` at all — it returns `{"next": "confirm"|"result"|"input"}` and lets the client route itself. Per-page dynamic URLs are already the client's responsibility there, so no plugin change is needed for that mode.
- Any built-in placeholder/templating syntax for paths (e.g. `{slug}`, `{permalink}`). The decision for this issue is that the plugin stays unopinionated about URL shape — the theme always supplies a finished string via `get_permalink()` or equivalent.
- Resolving session collisions when the same visitor has the same form key open in two browser tabs pointing at two different posts simultaneously (pre-existing limitation of the `(form_id, session_key)`-keyed session table, not introduced by this change, but now also affects which URLs are used).
- Any guarantee of correct behavior behind a full-page cache — `setTemplate()` triggers a session write (DB insert/update) on every GET of a page that calls it, same as the existing unconditional session-cookie issuance already does today.

### Bonus fix: `tests/bootstrap.php` was silently truncating `composer test`

While verifying the above, discovered that `tests/bootstrap.php` never defined the `WPINC` constant. Several classes (`Init/Endpoint.php`, `Init/AdminPage.php`, `Init/RestEndpoint.php`, `Init/Initializer.php`) start with the standard WordPress direct-access guard `if (!defined('WPINC')) { die; }`. The instant PHPUnit's autoloader touched any of those classes (e.g. `class_exists(RestEndpoint::class)` in `RestEndpointTest`), the entire PHP process called `die` — silently, with exit code `0` — truncating the suite mid-run with no failure reported. Confirmed via `git stash` that this pre-dates this issue's changes: `composer test` was only ever exercising the first 28 of 61 pre-existing test methods. Fixed by defining `WPINC` in `tests/bootstrap.php` alongside the other WordPress test constants; the suite now runs to completion (73 tests including the ones added here, 100% passing). Also added `home_url()` and `wp_parse_url()` stubs to `tests/bootstrap.php`, needed by the new `isSameHostOrRelative()` guard.
